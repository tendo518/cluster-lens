# 架构演进计划

> 状态：第一阶段及审查后的正确性修复已实现；目录 / 构建阶段及第二至四阶段待实施。当前模块边界见[运行架构](architecture.md)。FastAPI、前端构建及反向代理尚未引入；运行、配置和发布方式仍以 [README](../README.md)、[配置参考](configuration.md)及[集成契约](integration.md)为准。

## 1. 目标与依赖边界

目标是在不破坏节点兼容、历史数据和现有功能的前提下，用成熟组件替代手写 Web 基础设施，并建立可独立测试的业务与存储边界。采用模块化单体，不因架构调整引入微服务。

**纯标准库的强制约束只适用于分发到各节点的 agent，不适用于监控中心或前端。**

| 组件 | 依赖策略 |
| --- | --- |
| 节点 agent | 保持独立单文件、Python 3.6+ 和标准库；不要求节点安装 Python 包或前端工具 |
| 监控中心 | 允许成熟第三方依赖；拟采用 FastAPI、Uvicorn、Pydantic，版本与最低 Python 版本需验证后锁定 |
| 浏览器前端 | 使用独立的 frontend 源码与构建，目标为 TypeScript + Vite；仅分发构建结果，不要求服务器或 agent 节点运行 Node |
| 配置与发布工具 | 允许独立的受控依赖环境；对外 CLI 和产物变更必须与集成方协调 |

Python 项目由 uv 管理，当前开发入口已使用独立 uv 环境；目标目录明确分为 frontend、backend 和 agents，详见[目录与构建设计](project-layout-plan.md)。Python host 脚本已经从后端包移至 `agents/python/agent.py`，可选 Node 实现待协议一致性和分发前提就绪后再增加，当前不要求节点安装 Node。

中心和 agent 通过有版本的 JSON 协议交互，不共享运行环境，也不要求 agent 导入中心模型。中心使用 Pydantic 不意味着 agent 需要 Pydantic。现有中心 Python 3.9+ 是当前实现要求，不预先承诺所有未来框架版本仍支持它。

## 2. 当前实现与待解决问题

当前中心使用标准库 ThreadingHTTPServer / BaseHTTPRequestHandler，同时提供网页、静态资源和 API；前端为原生 JS / CSS / SVG，历史保存在 SQLite。

静态资源和 API 同源、同进程不是问题本身。需要改进的是：

- HTTP 层仍手写路由、请求解析、请求限制、viewer 鉴权与错误响应，后续用标准框架替换。
- 报告处理、状态与历史用例已集中到 MonitoringService，调度独立于业务，SQL 聚合与历史响应组装分离；HTTP 不直接访问 Store。
- 前端 API 调用、页面状态与视图操作仍需模块化，降低修改时的联动范围。
- 引入中心依赖后，需要完善可重复构建、锁定依赖和运行环境验证，而不是继续假定解压源码即可运行。

SQLite 当前不是必须替换的瓶颈。已有 WAL 和写入控制应保留；本轮不引入 PostgreSQL、Redis、消息队列或容器编排。

## 3. 目标结构

```text
浏览器
  │ 同源访问
  ▼
HTTP 入口（初期可由应用承担；可选增加 Caddy）
  ├── 页面、静态资源、公开展示配置
  └── API → FastAPI + Uvicorn
               ├── HTTP / 鉴权 / 请求响应模型
               ├── 业务服务：报告处理、状态判定、历史统计
               └── 存储：SQLite 事务、查询与清理

节点 agent ── HTTP(S) / 独立节点令牌 ──→ 上报 API
```

仍按一个应用版本组织和发布中心、前端与 agent；部署方可以只更新中心，不强制所有节点同时升级。

### 中心分层

建议在现有运行包内逐步建立以下职责，具体目录在实现时确定，不为命名重排破坏公开入口：

| 模块 | 职责 | 不应承担 |
| --- | --- | --- |
| API / transport | 路由、身份认证、请求限制、输入输出模型、HTTP 错误映射 | 直接编写统计 SQL、实现监控规则 |
| services | 报告接收、去重与顺序规则、节点状态、历史与统计用例 | 依赖 Request / Handler 对象 |
| storage | 连接生命周期、事务、SQL、保留期清理和备份接口 | 决定 HTTP 状态码 |
| config / UI | 配置校验、公开展示数据、安全渲染或启动资源生成 | 读取部署 inventory、暴露凭据 |
| lifecycle | 初始化、关闭、后台清理任务与资源释放 | 隐式迁移账户或历史路径 |

先提取现有行为，再替换 HTTP 层；不要求一次重写全部模块，不为每个类机械增加抽象接口。

初期采用单 worker。当前存在进程内节点状态，不能直接用多 worker 假装横向扩容；以后扩展前必须明确共享状态和后台任务归属。同步 SQLite 操作应通过适当的同步路由 / 线程执行机制处理，避免阻塞异步事件循环。报告确认不能因为增加异步任务而退化为“尚未完成必要处理就返回成功”。

### 前端

先保留现有交互和技术选择，按 API 客户端、状态 / 浏览器偏好、节点 / 进程 / 历史视图、图表与样式拆分模块。不将 React、Vue 或其他框架迁移设为本轮前提。

如引入构建工具，只在开发 / 构建端使用，发布包包含最终资源。若首页改为静态托管，公开 UI 配置由应用生成独立启动资源，先于外观初始化加载，保持标题、图标和主题首屏行为。不能为了方便直接暴露 server.json 或把令牌打入前端包。

### HTTP 入口与静态托管

Caddy 是可选的后续部署能力，不是分层重构的前置条件。需要 TLS、压缩、缓存或独立访问日志时，再由部署方引入：

- 浏览器仍使用同一来源，避免无必要的 CORS 和跨域认证。
- 代理提供静态资源并转发 API，应用可只监听 loopback。
- 代理不得绕过 API 鉴权、请求体限制或可信来源边界。
- 公共配置和认证响应不能套用长期静态缓存；仅对合适的版本化静态资源设置缓存。

## 4. 必须保持的契约与数据

- 保持现有 agent 可上报；不为 URL 美观强制修改上报地址。若协议确需变化，显式版本化并先提供兼容中心，再升级节点。
- 保持 viewer 与逐节点令牌隔离、身份绑定、时间校验、去重、范围校验、报告大小限制及 HTTPS 验证行为。
- 保持 `CLUSTERLENS_VIEWER_TOKEN` 与 viewer_token 的配置语义，不记录或公开令牌。
- 保持数据库路径和历史含义，未知 / 离线不填 0，统计和 CSV 定义不因重构改变。
- 保持浏览器偏好键、置顶、筛选后分页、导航和无闪烁首屏行为；配置文本继续转义，图标继续限制为安全的自包含资源。
- viewer 令牌按可信内网的简单访问限制持久保存在 localStorage，支持旧会话迁移、退出和 401 清除；本轮不引入服务端会话 / Cookie 体系，不因网络故障清除登录。
- 保持应用与部署单向依赖：部署方调用公开 CLI / JSON / 发布产物，不导入应用内部代码。
- Python 包名、发行标识、远端路径和服务名不是本轮改名目标。

## 6. 发布与迁移边界

首个目标交付方式选为匹配中心 Python / 平台的离线 wheel 集，构建端由 uv 锁定依赖，中心普通用户创建新的版本化环境并离线安装。平台和安装工具分发前提必须先核实；在线安装或容器作为后续扩展，不同时维护所有方式。不能把控制端的 `.venv` 直接复制到不同解释器 / 平台上。

当前无依赖 CLI 仍兼容 `python -B -S -m project_tools`；`-S` 会跳过常规 site-packages。外部适配器已经支持显式工具解释器（不加 `-S`）及预构建目录，describe 用于检查生成器契约，但依赖准备仍需由操作者按应用 uv 锁显式执行。引入第三方模型时必须把这一环境设为明确前提，不能只增加依赖却保留旧入口，也不能在工具中维护另一套配置 schema。

当前发布清单为 format_version=1，包含 server.tar.gz 和 agent.py。若新方案改变解释器、依赖交付、产物或启动约定，应先定义并测试新版契约，再更新集成方；不能只修改归档内容让旧安装器误以为兼容。详情的落地变更应写回[集成契约](integration.md)。

任何生产升级前，必须备份并核对有效配置、令牌、实际运行账户、数据库及 WAL 中的历史。采用隔离目录验证，保持原数据与身份；不把框架迁移与账户迁移、数据库改型、令牌轮换或时钟修改捆绑。升级失败时分别判断代码和数据是否可回退，不承诺数据库发生不兼容变化后仍能直接换回旧代码。
